# Context for the review

- **What it is**: an unofficial app for the NRGkick mobile EV charging cable (second generation, WiFi) by DiniTech.
  Three drivers, all class `evcharger` with `energy.evCharger`: `nrgkick` (second generation, the main driver) and
  two experimental drivers for the first generation, `nrgkick_connect` and `nrgkick_ble` (see the last section). The store texts state that the app is not affiliated
  with or endorsed by DiniTech GmbH. The app icon, driver images and app images use DiniTech's logo and product
  photos; the developer is asking DiniTech for permission and will replace them with own artwork if refused.
- **Network**: local only. The app talks to the NRGkick's documented local JSON API over HTTP on port 80
  (`GET /info`, `/values`, `/control`), the only transport the device offers. No cloud service and no third-party
  endpoints. The only permission, `homey:wireless:ble`, is for the first-generation Bluetooth driver. HTTP Basic Auth is used when the user enabled "Authentication (JSON)" in the
  NRGkick app; the credentials are stored in the device settings (password field).
- **Discovery and manual address**: the NRGkick announces itself over mDNS (`_nrgkick._tcp`, serial number in the
  TXT record). The pairing view lists found devices and also accepts an address by hand, because the charger often
  sits on another subnet or VLAN than Homey where mDNS does not reach. The app first connects without credentials
  and shows the standard login view only when the NRGkick answers 401; when the JSON API is off it shows how to turn
  it on. Homey does not always receive every TXT record (the serial number was missing through a UniFi mDNS proxy),
  so the serial is read from `/info` and a moved device is found again by asking the announced addresses. For that reason the discovery strategy is
  not linked to the driver's availability; the driver listens to it and updates a device's address when DHCP
  hands out a new one.
- **Polling**: the device offers no push. The app reads `/control` and `/values` every 30 s by default (10-300 s,
  device setting) and `/info` every 10 minutes, with exponential backoff on errors. Capabilities and settings are
  only written when a value changed.
- **Physical effect**: charging can be paused or resumed, and the charging current, an energy limit and the
  number of phases can be set, from the device, from Flow cards and from Homey Energy (`target_power`,
  `target_power_mode`). Homey is in charge and the last command wins: a target power becomes a charging current,
  and below 6 A (about 1380 W on one phase, set as the exclude range) charging pauses, because a car cannot charge
  with less. A pause caused by a low target power resumes when the target rises; a pause by the user holds.
  `target_power_mode` stays hidden and only marks when Homey Energy takes over: when it hands control back, the
  app restores the current and pause state from before.
- **Phase switching**: the phase count can only be changed when phase switching is enabled in the NRGkick app;
  otherwise the device refuses and its reason is shown. This was tested against a simulated device only, because
  the test unit has a single-phase attachment.
- **Hidden capabilities**: per-phase power and voltage, neutral current, frequency, power factor, extra
  temperatures and WiFi signal use `uiComponent: null`, so they stay available in Insights and Flows without
  crowding the device view.
- **SIM models (untested on hardware)**: NRGkick units with a SIM card also report mobile network and GPS data in
  `/info`. The app adds those capabilities only when the model type contains "SIM", and removes them otherwise.
  This part follows the vendor's API documentation and is tested against a simulated device only, because no SIM
  unit was available; the README and the release notes say so. The position is shown on the device and used for
  a *location changed* trigger (moved more than 100 m); it is not sent anywhere.
- **First generation (experimental, untested on hardware)**: no first-generation unit was available, so both drivers
  carry "(experimental)" in their name and are tested against simulated devices only; the README and store texts
  say so. `nrgkick_connect` talks to the NRGkick Connect WiFi bridge over HTTP, following DiniTech's "NRGkick
  Connect – JSON WEB API" (version 0.2): GET for data, one PUT per change with the NRGkick's Bluetooth PIN (stored
  as a password setting), and a UDP multicast question (239.255.255.250:1905, the vendor's discovery protocol) during
  pairing, and again (at most every 5 minutes) when the module stops answering, to follow it to a new address; the
  socket is closed after 3 seconds. The Connect API cannot tell whether a car is plugged in, so without charging
  power the state shows plugged in (or paused); the README says so. `nrgkick_ble` reads four GATT characteristics over Homey's
  Bluetooth, one short connection per read (default every 60 s, 30-600 s), and is read-only for now: switching
  charging is refused with an explanation. Its byte layout comes from evcc (MIT). A device setting "Debug logging"
  (off by default) writes the raw data to the app log, so testers can send it in with "Report a problem".
- **Store text on Bluetooth range**: the short Bluetooth range is the main limit of the Bluetooth driver (the
  cable often lies outside, Homey inside), so the store text states it as a limit, at the developer's request.
  The how-to (close the phone app) is on the pairing screen only.
- **Driver images and icons**: each driver has its own. The first-generation image is a drawing of that unit and
  the Connect image is the module on white; both are based on product pictures, as are the second-generation
  images. The developer has asked DiniTech for permission to use their product pictures and logo.
